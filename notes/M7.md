# M7 — Multi-Tool Workflows

## Feature I picked
- A "starred" filter: users can star individual notes and toggle a view showing only starred notes.

## Plan from chat

**Feature: Starred Notes Filter**

**Data model**
Add a `starred` boolean field (default `False`) to each note dict. This is the only schema change needed. Existing notes without the field should be treated as unstarred — use `.get("starred", False)` rather than direct key access.

**Route changes**

1. `POST /notes/<idx>/star`
   - Toggles `app.notes[idx]["starred"]` between `True` and `False`
   - Returns 302 redirect to home
   - Returns 404 if `idx` is out of range (including negative indices)

2. `GET /` (updated)
   - Reads optional `?filter=starred` query param
   - If present, passes only starred notes to the template
   - Passes a `filter_starred` boolean to the template so the filter link can display correctly

**UI changes**

Home page:
- Filter toggle link at the top: "Show starred only" / "Show all notes" depending on current state
- Per note: a star button (☆ unstarred, ★ starred) as a small `<form method="POST">` — not a link, since starring is a state change
- Empty state when filter is active and nothing is starred: "No starred notes yet."

New note page: no changes — notes start unstarred.

**Edge cases**
- Index out of range on star route → 404
- Negative index on star route → 404 (Python allows negative list indexing; guard explicitly)
- Filter active with zero starred notes → show empty-state message, not a blank page
- Existing test-seeded notes without `starred` key → `.get("starred", False)` handles it
- Starring while in filtered view removes the note from visible list immediately — correct behavior

**Files to change:** `app.py`, `templates/home.html`

No new dependencies. No changes to existing tests.

## Execute in Claude Code
- Branch: `m7-starred-filter`
- One thing Claude flagged that the chat plan missed: the template loop needs the *original* note index even when filtering, but passing the filtered subset of `app.notes` loses the original positions. Passing `enumerate(app.notes)` tuples to the template and unpacking `(idx, note)` in the loop is the fix — Chat's design thought at the route level and never mentioned this template-layer detail.

## Review in chat
- Chat flagged that `app.notes[idx]` would raise `IndexError` on a negative integer index (e.g. `-1`) since Python allows negative list indexing — a valid `<int:idx>` Flask parameter that bypasses the length check. I added `if idx < 0 or idx >= len(app.notes): abort(404)` to guard both ends.

## Workflow retro

The four lanes each did what they're best at. Chat planned cleanly — no files, no commit pressure, just a page of clear decisions with edge cases I wouldn't have thought to list myself. Claude Code implemented without needing me to explain Flask routing or Jinja syntax. Copilot handled the two-second edits I'd have typed anyway. Chat reviewed the diff with fresh eyes and caught the negative-index edge case I would have shipped.

The place one tool caught what another missed: Claude Code flagged that the template loop needed original indices when filtering — something Chat's design never mentioned because Chat thinks at the route level, not the template-loop level. Claude Code is in the code; Chat is above it. The handoff between them is where the real implementation detail lives, and that handoff is where I had to think hardest as the conductor.

If I re-did this feature, I'd give Chat's design brief a "what can go wrong in the implementation?" follow-up before handing it to Claude Code — not to generate code, just to surface gotchas. That one index issue cost me a cycle of back-and-forth in plan mode.

Most of my time as conductor was at the handoff moment: re-reading Chat's design and wrapping it in the M3 constraints block before pasting it into Claude Code. That pause was the right place to spend time. If I'd pasted the plan raw, Claude Code would have built something that technically worked but missed the filter edge case.

The parallel sessions surprised me — less valuable than I expected. I thought I'd get two features for the price of one, but the reality was that the second session sat idle while I was focused on the first. The lesson isn't that parallelism is useless; it's that you need to actually disengage from the first session long enough to give the second one the attention it needs. That's harder than it sounds when session one is still waiting on you.
